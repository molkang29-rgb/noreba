## 2. 운임 정책

### 단일 사업자

- 도쿄메트로만 이용: 도쿄메트로 GTFS 운임 규칙 사용
- 도에이만 이용: 도에이 GTFS 운임 규칙 사용
- 다른 운영사의 노선이 라우팅 데이터에 들어오더라도, 해당 사업자 운임 모델을 검증하기 전에는 다른 운영사 운임과 임의로 합산하지 않고 통합 운임을 미확인으로 둔다.

### 도쿄메트로 ↔ 도에이 예외

현재 앱 정책으로 지원하는 유일한 교차 사업자 조합이다. 연속 운영사 구간별 운임을 합산하고, 성인 70엔 환승 할인을 여정당 한 번 적용한다. 도쿄도 교통국의 공식 환승 할인 안내는 도에이와 도쿄메트로 연결 운임에서 70엔을 할인한다고 명시한다.

- 도쿄도 교통국 운임: https://www.kotsu.metro.tokyo.jp/subway/fare/regular.html
- 도쿄도 교통국 환승 할인: https://www.kotsu.metro.tokyo.jp/subway/fare/discount.html
- 도쿄메트로 일반 운임: https://www.tokyometro.jp/lang_kr/ticket/types/regular/index.html
- 도쿄메트로 도에이 환승권 할인: https://www.tokyometro.jp/lang_en/ticket/types/connection/index.html

다른 사업자 사이에도 별도 연락 운임이나 할인 제도가 존재할 수 있으나, 현재 NOREBA에서는 공식 규칙을 별도로 모델링하지 않은 교차 사업자 조합을 합산하지 않는다. 이는 “다른 사업자 할인은 현실에 없다”는 주장이 아니라, 앱이 미검증 금액을 확정 운임처럼 표시하지 않기 위한 정책이다.

### GTFS `payment_method`의 올바른 의미

GTFS 및 GTFS-JP 표준에서 `fare_attributes.payment_method`는 운임 매체(IC/종이)가 아니라 결제 시점을 뜻한다. `0`은 승차 후 결제, `1`은 승차 전 결제다. 출처: https://gtfs.org/documentation/schedule/reference/ 및 https://www.gtfs.jp/testsite/fix/format-reference_headers/developpers-guide/format-reference.html

따라서 이전 구현처럼 `payment_method=1`을 IC, `payment_method=0`을 종이 승차권으로 해석하면 안 된다. 현재 피드의 요금 금액은 운영사 공식 IC 요금표와 대조해 IC 요금 값으로 사용하고, 별도의 종이 승차권 요금 값이 피드에 독립적으로 인코딩되지 않았으므로 `paperFare`는 미확인(null)으로 남긴다. 이에 따라 도덴 아라카와선의 `payment_method=0` 가격 168엔도 IC 요금으로 정상 해석된다.

506엔 산식:

`도에이 178 + 메트로 178 + 도에이 220 − 메트로↔도에이 할인 70 = 506엔`

이 여정의 회귀 테스트는 실제 통합 그래프에서 얻은 운행 연결·환승 연결을 사용해 `makeRoute()` 운임 합산을 검증한다. 후보 경로 탐색의 상한 및 스케줄링과 운임 회계를 분리하기 위해 이 특정 운임 회귀의 시각은 합성 단조 증가 값이다. 따라서 이 테스트는 전체 운임 계산을 확인하지만, 기본 후보 탐색이 해당 경로를 항상 결과 카드에 노출한다고 증명하지는 않는다.

중요한 잔여 검증: 도쿄메트로↔도에이를 여러 번 반복해 넘나드는 모든 여정에 70엔을 항상 여정당 한 번만 적용하는 것이 각 개별 공식 운임 사례와 일치하는지는 아직 충분히 표본화되지 않았다. 현재 구현 정책은 한 번 차감이며, 추가 Yahoo!/공식 노선별 샘플을 통해 계속 확인해야 한다.

IC 카드로 개찰구를 나갔다가 다시 들어가는 방식의 환승은 특정 역에서 60분을 넘기면 환승 정산이 끊기고 새 운임이 필요하다는 공식 안내가 있다. 현재 NOREBA는 승객의 개찰구 이탈·재입장 여부나 체류 시간을 모델링하지 않으므로, 운임은 정상적인 연속 환승으로 이용한다는 전제의 추정치다. 단순히 열차 시간표상 환승 대기 시간이 60분을 넘는다는 이유만으로 자동으로 운임을 나누지는 않는다. 공식 안내: https://www.kotsu.metro.tokyo.jp/pickup_information/news/subway/2026/sub_p_2026012812378_h.html

## 4. 한국어 역명 보완

이전 버전에서 한국어 표시명이 없었던 역 노드 43개는 도에이 지하철 본선이 아닌 닛포리·도네리 라이너 및 도덴 아라카와선에 속했다. 초기 한국어 역명 사전은 도에이 지하철 역 위주였기 때문에 이 두 노선의 표기가 빠져 있었다. `data/station-korean.json`에 한국어 표기 42개를 추가했으며, 구마노마에가 두 노선에 각각 존재하므로 총 43개 역 노드가 보완됐다. 현재 통합 역 334개 중 한국어 표시명이 비어 있는 노드는 0개이며, 통합 감사 스크립트가 이를 강제 검사한다.

외부 사업자 연결 참조 177건은 기록만 유지하며, 이번 릴리스에서는 라우팅에 통합하지 않는다. 이 작업은 별도 후속 과제로 보류한다.

## 5. 회귀 테스트

현재 자동 테스트는 다음 항목을 확인한다.

- 통합 역·노선·trip·fare ID 중복 및 참조 무결성
- GTFS 출발·도착 시간이 없는 승객용 ride-service의 부재
- 도쿄메트로 역 그래프 전체 reachability
- 주중/주말/공휴일 달력, 첫차/심야 서비스 날짜, 자정 통과
- 직접 경로, 경로 식별 중복 제거, 환승 연결 시간과 도착 시각 정렬
- 도쿄메트로 ¥178/¥252, 도에이 지하철 ¥178/¥220, 닛포리·도네리 라이너 ¥168/¥231, 도덴 ¥168 표본
- 도쿄메트로↔도에이 조합 운임 ¥506
- 제3의 사업자가 포함된 교차 사업자 여정은 IC/종이 운임 모두 미확인으로 유지
- `payment_method=0`을 종이 승차권으로 오해하지 않음

반복 실행 명령:

```powershell
npm.cmd test
npm.cmd run audit:feeds
npm.cmd run lint
npm.cmd run build
```

`npm.cmd run audit:feeds`는 Python 3 표준 라이브러리로 원본 GTFS ZIP을 직접 검사한다. `npm.cmd test`는 가공된 통합 데이터 감사와 경로 엔진 회귀 테스트를 수행한다. 린트/프로덕션 빌드는 의존성을 설치한 로컬 환경에서 별도로 수행해야 한다.
